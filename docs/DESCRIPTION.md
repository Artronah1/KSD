# ksd — Go-демон Killswitch

Полный проект сгенерирован и упакован в `ksd.zip`.

---

## Сборка (для твоего устройства)

```bash
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o ksd .
```

Нулевые зависимости (в `go.mod` нет `require`). Бинарник весит около 2,5 МБ, что для устройства с 512 МБ RAM пустяк.

---

## Структура кода (12 файлов .go, около 2 900 строк)

| Файл | Ответственность |
|---|---|
| `config.go` | Типизированная конфигурация и валидация; заменяет примерно 250 строк `config_get` и регулярных выражений |
| `uci.go` | Разбирает UCI-файл напрямую, без вызова `uci` через exec |
| `nft.go` | Обёртка над `nft` и минимальная JSON-модель (декодируется по требованию, поэтому не ломается при смене схемы) |
| `ruleset.go` | Декларативная модель правил и рендеринг |
| `verify.go` | Верификация, **выводимая из модели** |
| `wan.go` | Определение WAN через ubus и `ip route` |
| `state.go` | Единый JSON-файл состояния вместо десятка разрозненных файлов в `/var/run` |
| `install.go` / `daemon.go` | Установка и резидентный цикл |
| `main.go` | CLI |

## Три ключевых проектных решения

### 1. Правила как контракт

Каждое правило несёт `comment`, а верификация сравнивает последовательность comment'ов в модели с ядром:

- параметры цепочек совпадают
- все comment'ы на месте
- **относительный порядок полностью совпадает**
- счётчики существуют
- содержимое динамических set'ов соответствует ожидаемому

Одна лишь проверка относительного порядка покрывает все причинные утверждения вида «A должно идти перед B» из старого jq-кода.

Когда ты меняешь правило, ты меняешь его в одном месте, и верификация подстраивается автоматически. Старой проблемы, когда генератор и верификатор писались отдельно и расходились, больше нет.

### 2. WAN и шлюз живут в set'ах

`ks_wan` / `ks_wan_gw` — это nft set'ы, а в тексте правил остаётся только `oifname @ks_wan`.

При смене WAN обновляются только элементы set'ов: набор правил не пересобирается, conntrack не сбрасывается. Multi-WAN тоже превращается из «сгенерировать N правил» в «добавить один элемент».

### 3. Слоистый fail-close

| START | Компонент | Поведение |
|---|---|---|
| 15 | `ksd-boot` | Устанавливает `/etc/ksd/emergency.nft` (статический файл, без логики, без зависимостей) |
| 60 | `ksd run` | Устанавливает baseline, затем пробует full; при успехе уничтожает emergency-таблицу |
| — | Страховка | Если бинарник ksd удалён или не запускается (не та архитектура, SIGILL), emergency-таблица остаётся в силе: у устройства нет связи, но **ничего не утекает** |

## Уже внесённые исправления по итогам ревью

- **P0-1** — резидентный процесс читает источник напрямую каждые 5 с, поэтому cron не нужен
- **P0-2** — baseline по-прежнему применяется через `nft -f`, и только при сбое включается запасной путь
- **P0-3** — предохранитель `full_fail_max`
- **P1-4 / P1-5 / P1-6** — conntrack сбрасывается только когда набор **сужается**, а при сбоях сразу происходит деградация
- **P1-7** — подсчёт и лог с ограничением частоты разделены на два правила
- **P1-8** — NTP разрешён и в full-режиме
- **P1-10** — конфликт с flow offload сообщается при старте как CRITICAL
- **P2-1 – P2-7** — все

Следующие опции **удалены**:

```
cache_ttl_hours
empty_source_threshold   (счётная семантика)
monitoring_*
semantic_verify_enabled
```

В резидентном процессе проблем, которые они компенсировали, больше нет. Полная таблица соответствия старых и новых опций находится в `CONFIG.md`.

## Одна вещь, о которой нужно знать

### Ловушка с `nft flush table` (присутствовала уже в shell-версии)

`nft flush table` **очищает только правила**. Цепочки, set'ы и счётчики сохраняются (документация nftables говорит об этом прямо).

Поэтому при повторном применении набора правил `add set ... elements = {...}` ничего не делает.

По этой причине ksd **не полагается** на элементы, встроенные в файл с правилами: содержимое WAN, шлюза и эндпоинтов всегда загружается отдельно через `flush set` и `add element` (см. `applyDynamicSets`).

В разделе 8 `BUILD.md` это описано вместе с запасным вариантом изменения.

## Порядок первого развёртывания

Следуй разделу 3 `BUILD.md`:

1. `ksd dry-run`, чтобы просмотреть правила
2. `ksd baseline`, чтобы убедиться, что ты не заблокировал себя
3. Только после этого `service ksd start`

Лучше всё время держать серийную консоль или другой канал управления, не проходящий через killswitch.
